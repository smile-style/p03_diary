# 生活记录小程序（wx_daily）设计文档

日期：2026-11-06
状态：草稿，待确认

## 1. 为什么做

发起人自己有这个需求：生活里发生的事，过一段时间就记不清了。

典型例子：十五五规划发布那天，发起人在 XMind 里摘抄了很多段落，梳理出几个投资方向，也看好其中一条路线。时间一久，这些就忘了，也没再回头看。

XMind 的两个痛点：

1. **文件存在哪里找不到，换了设备就看不了。**
2. **太乱。** 今天是十五五规划，明天又有新的大事件，各种事混在一起，缺少一个结构感强的整理方式。

所以要做的不只是一个能把事情记下来的工具，更要让人**过一段时间还能找回来、想起来**。

开放给其他人注册使用，但每个人的记录**只有自己能看**，用户之间不互相可见。

## 2. 目标、非目标、反目标

### 目标（第一版：微信小程序）

- 用户能用微信登录，数据存在云端，换设备登录后能看到全部记录。
- 记录围绕「分类 → 主题 → 记录」组织，主题可以长期追加记录。
- 记录支持摘抄卡片（摘抄段落 + 自己的想法）、自由正文、图片、链接、`#标签`。
- 摘抄卡片可以标记 **★看好**，之后能单独筛出所有标过看好的内容。
- 四种回看方式：时间线、日历、主题（含主题详情的小时间线）、标签。
- 全文搜索：能搜到正文、摘抄、想法里的关键词，也能按标签搜。

### 非目标（第一版不做，但架构上不能堵死）

- Android App（第二阶段）、iOS、网页版等多端适配（第三阶段）。
- AI 自动提取标签或推荐标签（以后可能升级为「自己打 + 自动推荐」）。
- 分享、公开广场、多人协作。
- 离线编辑与同步冲突处理。

### 反目标（如果出现这些，就算功能都能跑也是失败）

- **一个用户能看到另一个用户的记录。**
- **记录丢失**：已保存的内容找不回来。
- **数据和账号被锁死在微信里**，导致做 Android App 时要重做账号或迁移数据。
- **写一条记录比在 XMind 里还麻烦**，或者记了以后还是找不到。

## 3. 约束

- **平台路线**：先微信小程序，再 Android，最后多端。第一版的前端代码要能直接编译成 Android App。
- **注册主体**：按个人主体注册小程序。因为内容只有自己可见、不涉及用户间内容发布，所以属于「记录类工具」，个人主体大概率能过审（依据是开发者经验文章，没找到官方原文确认）。
- **内容安全**：微信把用户输入的日志、相片都算作 UGC，必须接入微信内容安全接口（文字用 `msgSecCheck`，图片用 `imgSecCheck` 或 `mediaCheckAsync`），而且只能在服务端调用。没接的话，提交审核时大概率会被驳回。
- **备案**：小程序后端的域名需要 ICP 备案，服务器需要在国内。

### 3.1 现有条件（2026-11-06）

- **还没有小程序 AppID**，也**没有营业执照**。先开发，上线前再按个人主体注册。
- **没有域名**。正式上线需要域名、ICP 备案和 HTTPS，备案通常要几周，这是上线前的关键路径。
- **已有一台云服务器**。开发阶段直接通过 IP 访问测试，本机改 hosts 绑定一个测试域名。
- **服务端用 Docker 部署**（发起人指定）。

对开发的影响（以下是我的决定）：

- **开发阶段**：在微信开发者工具里关闭「校验合法域名」，直接连服务器 IP 或 hosts 域名。注册 AppID 之前，先用微信提供的小程序测试号调试登录。
- **内容安全检查做成可开关**：没有正式 AppID 时，用一个"全部通过"的替身实现；拿到 AppID 后换成真实接口。提交审核前必须切到真实接口，并录制拦截演示。
- **部署**：用 `docker compose` 编排后端服务和 PostgreSQL。
- **图片存储先放服务器本地磁盘**（挂载 Docker 数据卷），但做成存储接口，以后可以无痛换成 COS 这类对象存储。
- **数据库定期自动备份**到服务器上的另一个目录。这是针对反目标「记录丢失」的最低保障。

## 4. 技术方案（已选：A）

考虑过的方案：

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. uni-app + 自建后端（已选）** | 前端 uni-app（Vue 3），一套代码出小程序和 Android App；后端自建，数据库 + 对象存储 | 数据和账号完全自己掌握，多端共用同一份数据，搜索和筛选好做；代价是要租服务器、域名备案、自己维护后端 |
| B. uni-app + uniCloud | 前端同 A，后端用 DCloud 云服务 | 不用管服务器、上手快；但后端绑定 DCloud，中文全文搜索弱，以后换平台成本高 |
| C. Taro（React）+ 自建后端 | 同 A，前端改用 React | 适合熟悉 React 的人；国内 uni-app 生态更成熟，做 App 更顺 |

已排除：原生小程序 + 微信云开发（代码搬不到 App，数据和账号绑在微信里，违背多端路线）；Flutter（对小程序支持不成熟）。

**选 A 的理由**：最初的痛点就是"换设备看不到"，长远目标又是多端，所以数据和账号放在自己的后端最稳。

## 5. 产品设计（已和发起人确认）

### 5.1 数据结构

```
用户
 └ 分类（少而固定，可增删改，如：投资 / 学习 / 好文章 / 生活）
     └ 主题（一件事，可长期追加，如：十五五规划）
         └ 记录（某一天写的一条）
             · 日期（默认今天，可改）
             · 正文（自由书写，可选）
             · 摘抄卡片 × N：摘抄段落 + 我的想法 + ★看好标记
             · 图片 × N
             · 链接
             · #标签（跨主题串联）
```

- 记录可以不属于任何主题（例如"晚上跑步 5 公里"），这类记录只出现在时间线、日历和标签里。
- 标签在正文、想法里用 `#xxx` 书写，输入 `#` 时提示用过的标签。
- ★ 标在单张摘抄卡片上，不是标在整条记录上。

### 5.2 界面

底部四个标签页：**时间线 ｜ 日历 ｜ 主题 ｜ 我的**。时间线和主题页右下角都有 ＋，用来新建记录。

1. **时间线（首页）**：顶部是搜索框（可以搜关键词和 `#标签`）。记录按日期倒序排列，每条显示日期、内容摘要、所属主题、标签和图片数。点主题跳到主题详情，点标签跳到标签页。
2. **日历**：月视图，有记录的日子下面显示小绿点，左右切换月份。点某一天，下方列出当天的记录。
3. **主题**：顶部是「★ 我看好的」入口。下面按分类分组列出各个主题，显示记录数、★ 数和最近更新时间。底部是常用标签和对应的数量。可以在这里管理分类和主题。
4. **主题详情**：这个主题的小时间线，可以一直往里追加记录（包括复盘）。顶部切换「全部 / 只看 ★」。
5. **标签页**：列出所有带这个标签的记录，按时间排列。
6. **写记录**：顶部选主题和日期，下面是正文，可以添加摘抄卡片。每张卡片包含摘抄段落、我的想法和 ★看好开关。工具栏有：摘抄、#标签、图片、链接。
7. **我的**：账号信息、分类管理等。

界面草图在 `.superpowers/brainstorm/` 里（不提交到仓库）。

## 6. 由开发者自行决定的部分

以下是我（Claude）替发起人做的决定，标注出来供确认：

- **后端技术栈**：Node.js + TypeScript，数据库用 PostgreSQL，Docker 部署。图片先存服务器本地，以后可换腾讯云 COS 等对象存储（见 3.1）。框架由开发者选择。
- **登录**：小程序用微信登录（`code2Session`），后端签发自己的登录凭证。用户表与微信 openid 解耦：openid 只是挂在用户上的一种登录方式。
- **账号迁移到 App**：个人主体小程序拿不到手机号快捷登录，也没有 unionid，所以第一版**只做微信登录，不加第二种凭证**。到 App 阶段，在小程序「我的」页生成一次性**绑定码**，用户在 App 里输入绑定码，并设置手机号或密码，绑定到同一个账号。第一版只需保证数据模型支持「一个用户多种登录方式」。
- **全文搜索**：每个用户的数据量不大，第一版用数据库自带的模糊匹配（例如 `pg_trgm`）即可，不引入专门的搜索引擎。
- **内容安全**：保存时由服务端调用检查接口。
  - 文字不通过：不入库，提示用户修改。**写的内容保留在本地草稿里，绝不丢失**。
  - 图片走异步检查：不通过就隐藏这张图，并提示用户。
  - 检查逻辑做成独立模块，不和微信耦合。App 阶段没有 openid，届时换用腾讯云或阿里云的内容安全服务。
- **草稿**：写记录时在本地自动保存草稿，避免误退出丢失内容。
- **全局「★看好」**：除了主题详情里的「只看 ★」，搜索支持「只看 ★」筛选，主题页顶部也有「★ 我看好的」入口，按时间列出所有标过看好的摘抄卡片。
- **删除**：删除记录、主题、分类前要二次确认。删除分类时，下面的主题保留，归入「未分类」组；删除主题时，下面的记录保留，变成不属于任何主题的记录。

其余如目录结构、接口设计、UI 细节和配色，都留给开发者。
